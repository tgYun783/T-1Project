### 누가 어떤 장면에서 쓰는가

취업 준비를 처음 하는 취준생(역할 `취준생`, 단일 역할)이 PC 브라우저에서 쓴다. 공고에 지원하기 전·면접 전에 자기 경험을 정리하고 자기소개서를 만들며, 그 자기소개서로 음성 모의면접을 본다. 플랫폼은 `desktop`(이유는 `docs/scenarios.yaml`).

### 핵심 흐름

로그인 → 이력서 템플릿 입력(F2) → 자기소개서 초안 생성(F3) 또는 기존 자기소개서 등록(F4) → 자기소개서 선택해 모의면접 시작(F5) → 질문마다 음성 또는 글자로 답변(F6), 건너뛰기·종료 가능(F7) → 결과 확인·자기소개서 보완(F8). 면접 중 내 카메라 화면은 보여 주기만 한다(F9).

| 단계 | 시작 상태 | 입력/행동 | 처리 | 기대 결과 | 다음 행동 |
| --- | --- | --- | --- | --- | --- |
| 이력서 | 로그인 | 가진 이력서 내용을 텍스트 폼에 입력, 저장 | 빈 글이면 경고 | 다시 접속해도 같은 내용 | 자소서 생성 또는 등록 |

| 답변 | 질문 표시 | 음성(녹음→서버→Gateway STT→전사 확인·수정) 또는 글자 | 저장 → LLM 호출 1회로 확인 상태 갱신·다음 행동 판단(꼬리질문 본질문당 ≤2, 전체 ≤12개·≤12분) | 다음 질문 또는 종료 | 답변 반복 / 종료 |
| 결과 | 면접 종료 | 결과 열기, 수정 제안 승인·거절 | 승인 시 자소서 본문 반영 | 기록·구체화된 경험·보완 항목 ≤3·수정 제안 | 지난 결과 다시 보기 |

### 기능별 저장할 정보와 권한

역할이 `취준생` 하나이므로 모든 데이터는 **만든 본인만** 읽고 바꿀 수 있다. 다른 사용자의 데이터는 보이지 않는다(서버에서 소유자 검사).

| 기능 | 저장 | 읽기/변경 |
| --- | --- | --- |
| F1 계정 | 이메일, 비밀번호 해시, 역할(취준생) | 본인 |
| F2 이력서 | 고른 항목 목록, 항목별 글, 수정 시각 | 본인. 저장 뒤 수정·항목 추가 가능 |
| F3/F4 자기소개서 | 본문, 출처(초안 생성/직접 등록), 바탕 이력서 참조, 수정 이력 | 본인. 여러 개 가능 |
| F5~F7 면접 세션 | 선택 자소서, 면접관별 본질문(확인 목적·근거 문장), 질문 순서, 질문·답변 기록(전사 원문·수정본), 항목별 확인 상태, 종료 사유, 대체 질문 사용 여부 | 본인 |
| F8 결과 | 구체화된 경험, 보완 항목(≤3, 답변 연결), 자소서 수정 제안과 승인/거절 상태 | 본인 |
| F9 카메라 | 저장하지 않음 | — |

### 잘못된 입력·실패 시 규칙

- 이력서: 항목 0개 또는 빈 칸 저장 → 경고 표시, 저장 안 함, 다시 입력.
- 자기소개서 등록: 빈 글 → 저장 안 함, 이유 표시.
- 자소서 초안 생성: AI 호출 실패(키 없음 포함) → 에러 표시, 초안 저장 안 함. 앱은 키가 비어도 기동한다.
- 본질문 생성 실패 → 기본 질문 템플릿 사용, "대체 질문 사용" 상태 기록.
- 답변 판단 AI 실패 → 학생 답 대기(다음 본질문으로 넘길지, 재시도 안내인지).
- 음성 전사 결과가 비면 → 다시 말하기 안내. 질문 다시 듣기·전사 재시도는 질문 수에 넣지 않는다.
- 카메라 없음·거부 → 검은 화면, 면접은 계속.
- 없는 주소 → 404. 로그인 전 보호 화면 접근 → 로그인 화면으로.

### 기능별 완료 조건

`docs/problem.yaml` features의 `done`이 기준이다. 요약: 이력서는 다시 접속해도 같은 항목·내용이 보이고 빈 저장은 경고로 막힌다. 초안·등록 자소서는 목록에 남는다. 면접 시작 뒤 첫 질문이 글자로 보이고 새로고침해도 같은 순서다. 글자로 답하면 다음 질문이 보이고 기록에 한 줄 추가된다. 어느 질문에서든 종료하면 결과 화면과 종료 사유가 남고 종합 점수는 없다. 수정 제안을 승인하면 자소서 본문이 바뀐 채 유지된다.

### 로그인과 역할

로그인 필요. 역할은 `취준생` 하나(학생 답 2026-10-29). `docs/scenarios.yaml`의 `account`와 docker 시드 계정 역할에 같은 이름을 쓴다. 회원가입·로그인은 이메일/비밀번호.

### 첫 화면 (`/`)

로그인하지 않은 사람이 열면 서비스 이름과 이 서비스가 해 주는 일(이력서 → 자기소개서 → 음성 모의면접)이 보이고 '회원가입'·'로그인'으로 갈 수 있다. 로그인 화면으로 바로 보내지 않는다. **서비스 이름과 한 줄 설명: 학생 답 대기(프런트 팀원 담당).**

### 주 사용 플랫폼

`desktop`. 이유는 `docs/scenarios.yaml`의 `platformReason`(학생 말 그대로).

### 사용자 핵심 흐름

`docs/scenarios.yaml` S1~S6(학생 확인 2026-10-29). 메뉴·버튼 이름은 임시이며 화면 구현 시 실제 이름으로 맞춘다.

### 기술 구성 (3단계에서 확정)

- 프런트: Vite + React + TypeScript + Tailwind v4 (팀원 `frontend` 브랜치, 아직 main 미반영).
- 서버: **NestJS**(학생 답 2026-10-29). 정적 프런트 빌드 결과를 같은 서버가 3000번 포트에서 함께 내준다(주최 측 실행은 app 하나만 노출).
- DB: MongoDB(팀원 설계). docker compose에는 `db` 서비스로 MongoDB를 두고 `DATABASE_URL`로 연결한다. 배포(Vercel)에서는 외부 MongoDB(예: 무료 등급 Atlas)가 필요하다 — 학생 계정으로 만들어야 함(학생 답 대기).
- AI: 서버만 `AI_GATEWAY_API_KEY`로 Vercel AI Gateway 호출. LLM(본질문 생성·답변 판단·자소서 초안), STT(OpenAI 전사 모델, 모델 이름은 Gateway 목록 확인 뒤), TTS(질문 읽기). 팀 예산 $10이므로 호출마다 대화 전체 대신 확인 상태와 최근 답변만 넘긴다(팀원 설계).
- `/__health`: 인증 없이 200, `{"releaseId": RELEASE_ID}`, `Cache-Control: no-store`.
- E2E: 글자 답변 경로로만 돈다(테스트 브라우저에 마이크·카메라·소리 없음). 흐름당 1분 안에 끝나도록 S5는 답변 1회 뒤 '면접 종료'.

### 시드 데이터 (docker 첫 기동 시 앱이 만듦)

취준생 계정 1개(`SEED_USER_EMAIL`/`SEED_USER_PASSWORD`), 그 계정의 이력서 1개(항목 2~3개), 자기소개서 1개, 끝난 면접 결과 1개(자기소개서 수정 제안 1개 포함). S2~S6이 이 데이터만으로 성립해야 한다.

### 구현 우선순위·제외·보류·가정

- 우선순위: **학생 답 대기.**
- 이번에 제외·보류할 범위: **학생 답 대기.**
- 아직 확인하지 않은 가정: (1) 자동 테스트는 글자 답변으로만 돈다. (2) 면접 질문 생성·답변 판단·자소서 초안은 모두 Gateway LLM 호출을 쓴다. (3) 시드 데이터는 위 네 가지다. (4) 음성 답변 길이 상한(녹음 시간)·전사 비용은 3단계에서 정한다. (5) F3 초안을 사용자가 고칠 수 있는지, 문항별인지 한 덩어리인지 — 학생 답 대기.

## 설치·실행

Node 22와 Docker가 필요합니다.

**로컬 실행** (서버만, MongoDB는 따로 띄우고 `DATABASE_URL`로 주소를 넘깁니다)

```bash
cd server && npm install && npm run start:dev
```

**docker 실행** (저장소 루트에서, 프런트·서버·DB를 함께 띄웁니다)

```bash
docker compose up -d --build
```

기동 후 2분 안에 `/__health`가 200과 `releaseId`를 돌려주면 정상입니다. 종료와 DB 초기화는 `docker compose down -v`.

**검사** (typecheck·lint·test, CI도 같은 명령을 돌립니다)

```bash
cd server && npm run check
```

## 팀 작업 방법

1. 초대 메일(또는 GitHub 알림)에서 **Accept invitation**을 누른다.
2. 저장소를 받는다.
   ```bash
   git clone https://github.com/tgYun783/T-1Project.git
   cd T-1Project
   ```
3. 작업은 각자 브랜치에서 한다. `main`에 직접 올리지 않는다.
   ```bash
   git checkout -b feature/작업이름
   # 수정 후
   git add <파일>
   git commit -m "설명"
   git push -u origin feature/작업이름
   ```
4. GitHub에서 `main`으로 Pull Request를 만들어 합친다. 대시보드와 주최 측 실행은 `main`에 올라간 것만 본다.
5. 작업 시작 전에는 항상 `git pull origin main`으로 최신 상태를 받는다.
